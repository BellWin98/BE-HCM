# 지식 메모 권한 부여 및 공개/비공개 설계

- 작성일: 2026-11-05
- 대상 저장소: BE-HCM, FE-HCM (두 저장소 모두 변경)

## 1. 의도와 배경

지금 지식 메모는 **ADMIN만** 쓸 수 있고, 메모 범위도 **작성자 본인**으로 한정돼 있습니다
(`KnowledgeAccessChecker.canAccess`는 role만 보고, `KnowledgeNoteService`는 모든 조회·변경을 `member_id`로
거릅니다).

관리자(서비스 운영자 본인)는 자기가 쓴 메모를 **다른 유저들도 보게** 하려고 합니다. 원하는 유저는 **자기
메모를 직접 생성·수정·삭제**할 수 있게 하려고 합니다. 이를 위해 두 가지를 도입합니다.

1. **유저별 권한 2종(조회 / 작성)**: 관리자가 유저마다 켜고 끕니다.
2. **메모별 공개/비공개**: 작성자가 정합니다.

권한은 role(USER, FAMILY)과 무관하게 **모든 일반 유저에게 똑같이** 적용합니다.

**성공 기준**
- 관리자가 회원 관리 화면에서 어떤 유저에게 "조회"를 켜 주면, 그 유저는 지식 메모 메뉴에서 다른 유저들의
  공개 메모를 볼 수 있습니다.
- "작성"까지 켜 주면 자기 메모를 직접 관리할 수 있습니다.
- 권한이 하나도 없는 유저에게는 메뉴가 보이지 않습니다.

## 2. 권한 규칙 (사용자와 합의한 내용)

### 2.1 관리자 (`MemberRole.ADMIN`)
- 권한 테이블과 무관하게 **모든 권한**을 가집니다.
- 모든 유저의 메모(비공개 포함)를 조회·수정·삭제할 수 있고, 메모를 생성할 수 있습니다.
- 메모 목록에서 **"내 메모" / "공개 메모" / "비공개 메모" 3가지 필터를 여러 개 함께 선택**할 수 있습니다.
  - 체크한 항목 중 **하나라도 해당하면 보이는 합집합 방식**입니다.
  - 처음에는 "내 메모" + "공개 메모"가 체크된 상태입니다.
  - "비공개 메모"를 체크하면 **모든 유저의 비공개 메모**가 보입니다(5.2, 5.3 참고).

### 2.2 일반 유저 (ADMIN이 아닌 모든 role)
관리자가 부여한 권한만 쓸 수 있습니다. 권한은 두 가지입니다.

| 권한 | 허용되는 동작 |
|---|---|
| 조회 (READ) | 본인 메모 전체 + **다른 유저의 공개 메모** 조회·검색 |
| 작성 (WRITE) | 본인 이름으로 메모 **생성**(이미지 업로드 포함), **본인 메모만** 수정·삭제(공개/비공개 전환 포함) |

- 남의 메모는 작성 권한이 있어도 수정·삭제할 수 없습니다.
- **다른 유저의 비공개 메모는 어떤 화면·API로도 보이지 않습니다.** 목록, 단건, 검색, 종목 패널,
  종목별 개수가 모두 해당합니다.
- 둘 중 하나라도 있으면 지식 메모 메뉴에 접근할 수 있습니다. 하나도 없으면 다음과 같이 처리합니다(기존과 같음).
  - 메뉴를 숨깁니다.
  - API는 403을 응답합니다.
  - 화면 라우트는 `/dashboard`로 돌려보냅니다.
- **작성 권한만 있고 조회 권한이 없는 경우**: 본인 메모만 보입니다.
- **"내 메모만 보기" 필터는 작성 권한이 있는 유저에게만** 보입니다. 조회만 가능한 유저에게는 자기 메모가
  없을 것이므로 보이지 않습니다.

### 2.3 공개/비공개
- 작성자가 메모마다 공개 또는 비공개를 정합니다. **새 메모의 기본값은 공개**입니다.
- 비공개 메모를 볼 수 있는 사람은 **작성자 본인과 관리자**뿐입니다.
- 관리자도 "비공개 메모" 필터를 체크했을 때만 다른 유저의 비공개 메모를 목록에서 봅니다.
- **기존 메모는 마이그레이션할 때 모두 공개로 설정합니다.** 배포 직후 조회 권한을 받은 유저가 관리자 메모를
  바로 볼 수 있게 하기 위해서입니다.
- 공개 여부를 바꾸는 것은 메모 수정에 해당합니다. 작성 권한이 있는 작성자나 관리자만 바꿀 수 있습니다.

## 3. 목표 / 비목표 / 안티 목표

**목표**
- 유저별 권한 2종(조회 / 작성) 부여·회수(관리자 화면)
- 메모별 공개/비공개
- 일반 유저용 "내 메모만 보기" 필터(작성 권한이 있는 유저)
- 관리자용 "내 메모 / 공개 메모 / 비공개 메모" 다중 선택 필터
- 권한에 따른 메뉴·버튼 노출, 그리고 **서버에서의 차단**

**비목표 (이번 범위 아님)**
- 특정 유저에게만 공유하는 기능. 공개는 "조회 권한이 있는 모든 유저"에게 공개된다는 뜻입니다.
- 메모 단위의 개별 권한. 권한은 유저 단위로만 부여합니다.
- 생성과 수정·삭제를 따로 나눈 권한(작성 하나로 묶음)
- 메모 목록 화면의 "새 메모" 버튼 신설
- 메모 댓글·리액션, 권한 변경 알림(푸시)

**안티 목표 (기능이 돌아가더라도 실패로 보는 것)**
- 비공개 메모가 작성자·관리자가 아닌 사람에게 **어떤 경로로든** 보이거나, 개수로라도 새는 경우
- 남의 메모를 권한 없이 수정·삭제할 수 있는 경우
- FE에서만 막고 BE는 열려 있는 경우. 실제 차단은 언제나 서버가 합니다.
- 관리자가 남의 메모를 수정했을 때 작성자가 관리자로 바뀌는 경우

## 4. 제약 (프로젝트 규칙)

- 스키마는 Flyway로만 관리합니다(`ddl-auto: validate`).
  - 다음 버전은 **V15**부터 씁니다.
  - **파일 하나에 DDL은 하나**만 넣습니다.
  - 기존 테이블을 `ALTER`할 때는 `ALGORITHM = INPLACE, LOCK = NONE`을 붙입니다.
- 인가 판정은 `KnowledgeAccessChecker` 한 곳에서 합니다(기존 주석의 원칙). `SecurityConfig` URL 규칙에
  중복해서 넣지 않습니다.
- 응답은 `ApiResponse<T>`로 감싸고, 오류는 `CustomException(ErrorCode.X)`로 던집니다. 메시지는 한국어로 씁니다.
- BE와 FE 모두 TDD로 진행합니다. BE에서 스프링 컨텍스트가 필요한 테스트는 `IntegrationTestSupport`를
  상속합니다.
- 로깅은 `@Slf4j`를 씁니다. 권한을 부여하거나 회수할 때는 감사 로그(info)를 남깁니다.
- 회원 삭제 경로(`AdminMemberService.deleteMember`)에서 새 권한 테이블의 행도 지웁니다(`toss_access`와
  같은 방식).

## 5. 설계

### 5.1 데이터 모델 (사용자가 아닌 제 판단으로 정한 부분)

`toss_access`(V8)와 같은 패턴입니다. 회원당 한 행을 두고, ADMIN은 행이 없어도 모든 권한을 가집니다.

**V15 — `knowledge_access` 테이블 생성**
```
id, created_at, updated_at,
member_id   bigint NOT NULL  (UK uk_knowledge_access_member, FK fk_knowledge_access_member)
can_read    bit NOT NULL DEFAULT 0
can_write   bit NOT NULL DEFAULT 0
granted_by  bigint NULL      (마지막으로 변경한 관리자 id. FK 없음 — toss_access 와 같은 이유)
```
- 두 권한이 모두 꺼지면 **행을 삭제**합니다. "행이 있으면 권한이 하나 이상 있다"는 상태를 유지하기 위해서입니다.
- 기존 회원에게는 시드하지 않습니다. 배포 후 관리자가 직접 지정합니다.

**V16 — `knowledge_note.visibility` 컬럼 추가**
```
visibility varchar(10) NOT NULL DEFAULT 'PUBLIC'   -- enum KnowledgeVisibility { PUBLIC, PRIVATE }
```
- `DEFAULT 'PUBLIC'`으로 기존 행이 모두 공개가 됩니다(2.3의 합의 사항).
- boolean 대신 enum 문자열을 쓰는 것은 제 판단입니다. 이후 공개 범위 값을 추가할 여지를 남기기 위해서입니다.

**인덱스**: 목록 조회가 "내 것 OR 공개"로 바뀝니다. 다만 가족 규모(수십~수백 건)에서는 풀스캔도 문제가 없으므로
**이번에는 인덱스를 추가하지 않습니다**(제 판단). 필요해지면 `(visibility, created_at)`를 별도 마이그레이션으로
추가합니다.

### 5.2 백엔드

**권한 판정 — `KnowledgeAccessChecker` 확장**
- `canAccess(principal)`: ADMIN이거나 `knowledge_access` 행이 있으면 true입니다.
  - 클래스 레벨 `@PreAuthorize`와 `/access`에서 씁니다.
  - DB를 조회하므로 `TossAccessChecker`처럼 `@Transactional(readOnly = true)`를 붙입니다.
- `canRead(principal)`, `canWrite(principal)`: ADMIN은 항상 true입니다.
- 메서드별 `@PreAuthorize`:
  - `GET /`, `GET /{id}`, `GET /stock-counts`: `canAccess`면 충분합니다. 보여줄 범위는 서비스가 정합니다.
  - `POST /`, `POST /images`, `PUT /{id}`, `DELETE /{id}`: `canWrite`
- **소유권 판정은 서비스에서 합니다.** `@PreAuthorize`는 "이 동작을 할 수 있는 회원인가"만 봅니다.
  "이 메모에 할 수 있는가"는 서비스가 메모를 읽은 뒤에 판단합니다.

**조회 범위 — `KnowledgeNoteService` / `KnowledgeNoteSpecs`**

서비스는 먼저 요청자의 **기본 범위**를 계산합니다.

| 요청자 | 기본 범위 조건 |
|---|---|
| 일반 유저, 조회 권한 있음 | `member_id = 나 OR visibility = PUBLIC` |
| 일반 유저, 조회 권한 없음 | `member_id = 나` |
| ADMIN | 필터에 따름(아래 표) |

목록 필터는 `GET /api/knowledge-notes`에 **다중 값 파라미터 `scopes`** 하나로 추가합니다.
- 받는 값: `MINE`, `PUBLIC`, `PRIVATE`. 예: `?scopes=MINE&scopes=PUBLIC`
- 각 값의 뜻:
  - `MINE`: `member_id = 나`
  - `PUBLIC`: `visibility = PUBLIC`
  - `PRIVATE`: `visibility = PRIVATE`
- 받은 값들은 **OR로 묶습니다**(합집합).
- **일반 유저**: 이 합집합에 기본 범위를 다시 AND로 겁니다. 그래서 어떤 값을 보내도 남의 비공개 메모는 절대
  나오지 않습니다. 예를 들어 `PRIVATE`만 보내면 본인 비공개 메모만 나옵니다.
  - FE는 "내 메모만 보기"를 켰을 때 `scopes=MINE`을 보내고, 껐을 때는 파라미터를 보내지 않습니다.
  - 파라미터가 없으면 기본 범위 그대로입니다.
- **ADMIN**: 기본 범위 없이 합집합만 적용합니다.
  - 파라미터가 없거나 비어 있으면 `MINE + PUBLIC`으로 처리합니다. 이때 결과는 "모든 유저의 공개 메모 + 내
    비공개 메모"입니다.

| ADMIN이 체크한 필터 | 보이는 메모 |
|---|---|
| 내 메모 + 공개 메모 (기본) | 모든 유저의 공개 메모 + 내 비공개 메모 |
| 내 메모 | 내 메모 전체(공개 + 비공개) |
| 공개 메모 | 모든 유저의 공개 메모 |
| 비공개 메모 | **모든 유저의 비공개 메모**(내 것 포함) |
| 내 메모 + 비공개 메모 | 내 메모 전체 + 모든 유저의 비공개 메모 |
| 공개 + 비공개 (또는 셋 다) | 모든 메모 |

- 합집합 방식은 사용자와 합의한 내용입니다. 이 방식에서는 "내 비공개 메모만"을 정확히 걸러 보는 목록은 만들 수
  없습니다. 이 경우에는 "내 메모"만 체크한 뒤 카드의 비공개 배지로 구분합니다.
- 다른 유저의 비공개 메모는 관리자가 "비공개 메모"를 직접 체크했을 때만 나옵니다.

- **`stock-counts`와 종목 패널**은 필터 없이 기본 범위를 씁니다. 따라서 ADMIN도 "공개 + 내 비공개"만
  집계됩니다. `countByStockSymbols`의 JPQL도 범위 조건을 받도록 바꿉니다(안티 목표: 개수 누출).
- **단건 계열**(`get`, `update`, `delete`): ADMIN은 범위 제한 없이 메모를 찾습니다. 일반 유저는 기본 범위
  안에서 찾고, 범위 밖이면 지금처럼 `KNOWLEDGE_NOTE_NOT_FOUND`를 응답해 존재 여부를 숨깁니다.
- **수정·삭제**: 일반 유저가 남의 공개 메모를 수정·삭제하려 하면 `KNOWLEDGE_NOTE_FORBIDDEN`(신규 ErrorCode,
  403)을 응답합니다. 이미 보이는 메모이므로 404로 숨길 이유가 없습니다(제 판단).
- 수정할 때 `member`(작성자)는 절대 바꾸지 않습니다.
- 로그에는 수정·삭제한 사람(actor)과 작성자를 함께 남깁니다.

**이미지 URL 재사용 차단 (제 판단)**
- **문제**: 지금은 URL의 `knowledge-notes/` prefix만 검사하고, S3 키에는 업로더 정보가 없습니다. 작성자가
  여럿이 되면 다음 일이 생길 수 있습니다.
  - 남의 공개 메모에서 본 이미지 URL을 자기 메모에 붙입니다.
  - 그 URL을 다시 빼거나 그 메모를 삭제하면 `imageCleaner`가 S3 파일을 지웁니다.
  - 결과적으로 남의 메모 이미지가 깨집니다.
- **대응**: 새 DDL 없이 검사 두 가지를 추가합니다.
  1. 생성·수정 시 **새로 붙는 URL**이 다른 메모의 `knowledge_note_image`에 이미 있으면
     `KNOWLEDGE_NOTE_IMAGE_INVALID`로 거부합니다.
  2. 수정·삭제 시, S3 정리 대상 가운데 **다른 메모가 아직 참조하는 URL**은 빼고 지웁니다(방어용 이중 확인).
- 업로드 기록 테이블이나 S3 키에 memberId를 넣는 소유권 추적은 이번에 하지 않습니다.

**DTO**
- `KnowledgeNoteRequest`에 `visibility`를 추가합니다. 값을 생략하면 생성 시에는 PUBLIC, 수정 시에는 기존
  값을 유지합니다.
- `KnowledgeNoteResponse`에 다음 필드를 추가합니다.
  - `visibility`
  - `author { id, nickname, profileUrl }`: 다른 사람 메모가 섞여 보이므로 작성자를 표시합니다.
  - `editable`(boolean): 요청자 기준으로 수정·삭제가 가능한지입니다. 작성 권한은 수정과 삭제를 묶으므로 필드
    하나면 됩니다. FE는 이 값을 버튼 노출에만 씁니다.
  - 응답 DTO가 지금 `from(note)` 정적 팩토리이므로, 요청자 정보를 받도록 시그니처를 바꿉니다.
- `GET /api/knowledge-notes/access` 응답을 `{ hasAccess, canRead, canWrite, isAdmin }`으로 확장합니다.
  - `hasAccess`는 하위 호환을 위해 유지합니다.
  - `isAdmin`은 FE가 관리자 전용 필터를 보일지 판단할 때 씁니다. role은 AuthContext에도 있지만, 지식 메모
    권한 판단은 한 응답에서 끝나도록 함께 내려줍니다(제 판단).

**관리자 API — `/api/admin/knowledge-access`**
- `AdminTossAccessController`와 같은 구조이고, `hasRole('ADMIN')`로 막습니다.
- `GET /`: 권한이 있는 회원 목록을 돌려줍니다.
- `PUT /{memberId}`, 본문 `{ canRead, canWrite }`: 두 값을 한 번에 설정합니다(멱등).
  - 둘 다 false면 행을 삭제합니다.
  - 대상이 ADMIN이면 아무것도 바꾸지 않고 성공으로 처리합니다(제 판단).
  - 행을 만들다가 UK 위반이 나면 기존 행을 다시 읽어 갱신합니다. 동시 요청이 와도 500이 나지 않게 하기
    위해서입니다.
- `AdminMemberResponse`에 `knowledgeAccess { canRead, canWrite }`를 추가합니다. 회원 목록을 만들 때
  `tossAccess`처럼 **한 번에 일괄 조회**해서 N+1을 피합니다.
- 회원을 삭제할 때 `knowledge_access` 행도 함께 삭제합니다.

### 5.3 프론트엔드

**권한 상태**
- `useKnowledgeAccess`가 `hasAccess`, `canRead`, `canWrite`, `isAdmin`을 함께 반환합니다. 캐시 키는 그대로
  씁니다.
- 메뉴(Header)와 라우트 가드(`RequireKnowledgeAccess`)는 지금처럼 `hasAccess`를 기준으로 합니다.

**메모 목록 필터 (`KnowledgeNotesPage`)**
- **일반 유저**: "내 메모만 보기" 토글 하나만 있고, `canWrite`일 때만 보입니다. 켜면 `scopes=MINE`을 보냅니다.
- **관리자**: "내 메모 / 공개 메모 / 비공개 메모" 3개를 다중 선택하는 필터(칩 또는 체크박스)를 둡니다.
  "내 메모만 보기" 토글은 따로 두지 않습니다.
  - 처음에는 "내 메모"와 "공개 메모"가 체크된 상태입니다.
  - **최소 하나는 체크된 상태를 유지합니다.** 마지막 하나는 해제되지 않습니다.
  - "비공개 메모"를 체크하면 다른 유저의 비공개 메모도 나온다는 점을 UI에서 알 수 있게 합니다. 문구는 구현할
    때 정합니다.
- 이 필터들은 기존 키워드·카테고리·종목 필터와 AND로 함께 동작합니다.
- 필터 값은 목록 쿼리 키에 포함해서 캐시가 섞이지 않게 합니다. 모두 기존 `KNOWLEDGE_NOTES_QUERY_KEY`
  prefix 아래에 두므로, 저장 후 무효화 방식은 그대로입니다.

**생성 진입점: 작성 권한이 없으면 숨기거나 막습니다**
- 현재 생성 진입점은 네 곳입니다.
  - `QuickNoteFab`
  - Header의 빠른 메모 버튼
  - `StockNotesPanel`의 "메모 쓰기" 버튼
  - PWA 공유 대상 페이지(`KnowledgeShareTargetPage`)
- 이 네 곳은 모두 `canWrite`일 때만 보이거나 동작합니다. 공유 대상 페이지는 지금 `hasAccess`로 판정하는데,
  공유는 곧 생성이므로 `canWrite`로 바꿉니다.
- `QuickNoteContext.openQuickNote` 안의 가드도 나눕니다.
  - `note` 없이 열면 생성이므로 `canWrite`를 확인합니다.
  - `note`를 넘겨 열면 수정이므로 그 메모의 `editable`을 확인합니다.
  - 폼 다이얼로그 자체의 렌더 조건은 `hasAccess`로 유지합니다.

**메모 카드 (`KnowledgeNoteCard`)**
- 작성자 닉네임과 프로필 이미지를 표시합니다. 내 메모는 따로 구분해 보여줍니다(문구는 구현할 때 결정).
- 비공개 메모에는 "비공개" 배지를 붙입니다.
- 수정·삭제 버튼은 응답의 `editable`이 true일 때만 보입니다.
- `StockNotesPanel`도 같은 카드 표시(작성자, 배지, 버튼 규칙)를 따릅니다.

**메모 작성/수정 폼 (`KnowledgeNoteFormDialog`)**
- 공개/비공개 토글(Switch)을 추가합니다. 새 메모의 기본값은 공개입니다.

**관리자 회원 관리 화면 (`AdminMembersPage`)**
- "토스 접근" 열 옆에 "지식 메모" 열을 추가하고, **조회 / 작성 체크박스 2개**를 둡니다. 모바일 카드 뷰도
  똑같이 합니다.
- ADMIN 행은 두 체크박스를 모두 체크한 채 비활성화합니다(토스와 같은 방식).
- 체크박스를 바꾸면 확인 창 없이 바로 `PUT`으로 저장합니다(제 판단).
  - 저장 중에는 그 회원 행의 체크박스를 비활성화합니다. 연속 클릭으로 오래된 값이 덮어써지는 것을 막기
    위해서입니다.
  - 작성을 켤 때 조회를 자동으로 켜지는 않습니다. 2.2 규칙대로, 이 경우 그 유저에게는 본인 메모만 보입니다.
- 저장 후에는 `adminMembers` 쿼리를 무효화합니다. 관리자 본인의 권한이 바뀌었을 수도 있으므로
  `KNOWLEDGE_ACCESS_QUERY_KEY`도 함께 무효화합니다.

**타입 / API**
- `types/knowledgeNote.ts`: `KnowledgeVisibility`, `KnowledgeNoteAuthor`를 추가하고, 응답·입력·검색 파라미터
  (`scopes`)·접근 상태 타입을 확장합니다.
- `lib/api.ts`:
  - `searchKnowledgeNotes`에 새 파라미터를 반영합니다.
  - Admin 섹션에 `getAdminKnowledgeAccess`, `updateAdminKnowledgeAccess`를 추가합니다.

## 6. 테스트에서 반드시 확인할 것

권한 매트릭스를 테스트로 고정합니다(BE 위주).

- **권한 없는 유저**: 모든 지식 메모 API가 403을 응답합니다. `/access`는 200이고 값은 모두 false입니다.
- **조회만 있는 유저**
  - 남의 공개 메모가 보입니다.
  - 남의 비공개 메모는 목록, 단건(404), 검색, stock-counts, 그리고 `scopes`에 어떤 값을 조합해 보내도
    **어디에도 나오지 않습니다**.
  - 생성·수정·삭제·이미지 업로드는 403입니다.
- **작성만 있는 유저**: 본인 메모만 보이고(남의 공개 메모는 안 보임), 생성·수정·삭제할 수 있습니다.
- **조회 + 작성 유저**
  - 본인 메모는 수정·삭제할 수 있습니다.
  - 남의 공개 메모를 수정·삭제하면 403, 남의 비공개 메모는 404입니다.
  - `scopes=MINE`이면 본인 메모만 나옵니다.
- **ADMIN**
  - 파라미터가 없으면 `MINE + PUBLIC`과 같은 결과입니다.
  - 5.2 표의 각 조합이 합집합대로 나옵니다.
  - `PRIVATE`은 모든 유저의 비공개 메모를 보여줍니다.
  - stock-counts에는 남의 비공개 메모가 집계되지 않습니다.
  - id로 남의 비공개 메모를 조회·수정·삭제할 수 있고, 수정한 뒤에도 작성자가 그대로 유지됩니다.
- **이미지**: 다른 메모에 붙은 URL을 새로 붙이면 거부됩니다. 공유 중인 URL은 S3에서 지우지 않습니다.
- **마이그레이션**: 기존 메모가 PUBLIC으로 읽힙니다.
- **관리자 API**
  - 두 값이 모두 false면 행이 삭제됩니다.
  - 같은 요청을 반복해도 결과가 같습니다(멱등).
  - 대상이 ADMIN이면 아무것도 바뀌지 않습니다.
  - 회원을 삭제하면 권한 행도 정리됩니다.
- **FE**
  - 권한에 따라 메뉴, FAB, 패널의 "메모 쓰기", 공유 페이지가 맞게 노출됩니다.
  - 일반 유저의 "내 메모만 보기"는 `canWrite`일 때만 보입니다.
  - 관리자 3종 필터는 `isAdmin`일 때만 보입니다. 기본 체크 상태가 맞고, 마지막 하나는 해제되지 않습니다.
  - 카드의 버튼은 `editable`을 따릅니다.
  - 관리자 화면의 체크박스 2개가 바르게 동작합니다.

## 7. 구현자에게 맡기는 부분

- 작성자 표시 문구, 배지 디자인, 필터 UI 형태(토글·셀렉트·탭), 관리자 화면 체크박스 배치(모바일 포함)
- `editable`을 계산할 때 권한 조회를 요청당 한 번으로 줄이는 방법(예: 서비스 진입 시 한 번 읽어 값 객체로
  넘기기)
- 신규 ErrorCode 이름과 메시지 문구
- 작업 순서와 이슈·브랜치 분리 방식. BE와 FE를 각각 별도 이슈로 진행하되, BE를 먼저 머지합니다.
